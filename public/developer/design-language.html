Living lab design language · updated 5 September 2026

Style the real lab, not a diagram of one.

The reviewed pilots retain their authentic models while applying lightly grouped working layouts, consistent controls, readable diagram typography and purposeful copy. This living guide shows how the shared visual language behaves in real labs.

Non-negotiable rules

These rules govern the shared language without standardising lab geometry. They apply to current and future labs, including literal reference specimens below.

01No unilateral state rails.

Fields receive complete semantic borders. Other feedback elements receive the full yellow, green or red surface, with a check or x for correct and incorrect states.

02Visual evidence first.

Current costs, distances, memberships, routes, signals and measurements belong on or immediately beside the represented model. Persistent working belongs on the right, then below the model on narrow screens. Keep the same calculation rows when assistance changes.

03Rounded actions, not pills.

Pills are reserved for syllabus chips. Buttons, tabs, mode controls and phase actions use the shared rounded rectangle.

04Reviewed references demonstrate the rules.

The guide shows full current lab code for Binary Number Practice, Coordinate Distance and Graph Search. Do not infer that a stripped-down mock is an acceptable replacement.

05Working stays persistent.

Interaction cues identify a target. Phase cards summarise a reached state or introduce a new decision. Predictions and calculations remain persistent outside them. Stage details may show a read-only working history; they never replace the working column.

06Use space before boxes.

Use padding within one parent surface. Lightweight cards can separate meaningful working steps or concepts: a full fine border, 12px padding, 8px corners and 10px between steps, without shadows or nested panels. Ordinary working uses regular ink-coloured text.

07Text must earn its place.

Keep goals, interaction hints, working and non-obvious interpretation. Improve the visual before adding prose that retells it.

08Vertical flow is allowed.

Keep working, evidence and explanation readable. Do not compress a complete lab merely to keep every section inside the first viewport.

09Diagram text is sized at the rendered scale.

Use 14px body, 12px labels and 11px annotations as the visual target. When a responsive SVG uses a viewBox, set its text units so the rendered type reaches those roles. Keep meaningful geometry, data mapping and model colours intact.

Starter token layer

The layer is comprehensive enough for shared chrome, fields, feedback, cues, phase cards, drag emphasis and Lab Kit compatibility. Local model colours remain local and named by their represented subject.

Light concept backgrounds

Use the approved base colour directly at 30% alpha: violet #7563a7 becomes #7563a74d. Paint it over white to retain its hue; do not further whiten the soft tint, stack translucent backgrounds, or reduce container opacity. Keep number tiles and shared-factor circles white inside the tinted main visual, with concept-coloured borders and ink for contrast. Use the matching opaque concept fill for working tokens. Do not dim the working tokens while answers are pending. These examples show the Prime Factors treatment.

Working and learning stages

One full-width activity top bar sits above the model and working columns. Keep the learner task on the left, with Reset beside it when needed. Put Working and its grey toggle on the right, immediately followed by stage markers when a real learning sequence exists. If a lab has multiple operated modes, the same control reflects the active mode while each mode keeps its own working state and earned availability.

function makeDraggableDialog(card, bounds) {
  const handle = card.querySelector('[data-dialog-drag]');
  let x = 0, y = 0, drag = null, moved = false;
  function move(dx, dy) {
    if (card.hidden) return;
    const r = card.getBoundingClientRect(), b = bounds.getBoundingClientRect();
    x += Math.max(b.left + 8 - r.left, Math.min(b.right - 8 - r.right, dx));
    y += Math.max(b.top + 8 - r.top, Math.min(b.bottom - 8 - r.bottom, dy));
    card.style.translate = `${x}px ${y}px`;
  }
  handle.addEventListener('pointerdown', e => {
    if (!e.isPrimary || e.button !== 0) return;
    moved = false;
    drag = { id: e.pointerId, x: e.clientX, y: e.clientY };
    handle.setPointerCapture(e.pointerId);
  });
  handle.addEventListener('pointermove', e => {
    if (!drag || e.pointerId !== drag.id) return;
    const dx = e.clientX - drag.x, dy = e.clientY - drag.y;
    if (!moved && Math.hypot(dx, dy) < 4) return;
    moved = true;
    move(dx, dy);
    drag.x = e.clientX; drag.y = e.clientY;
  });
  function end(e) {
    if (!drag || e.pointerId !== drag.id) return;
    if (e.type === 'pointercancel') moved = true;
    drag = null;
    if (handle.hasPointerCapture(e.pointerId)) handle.releasePointerCapture(e.pointerId);
  }
  handle.addEventListener('pointerup', end);
  handle.addEventListener('pointercancel', end);
  handle.addEventListener('lostpointercapture', end);
  handle.addEventListener('click', e => {
    if (moved && e.detail !== 0) { moved = false; return; }
    const r = card.getBoundingClientRect(), b = bounds.getBoundingClientRect();
    move(r.left + r.width / 2 < b.left + b.width / 2 ? b.right - 8 - r.right : b.left + 8 - r.left, 0);
  });
  handle.addEventListener('keydown', e => {
    const direction = { ArrowLeft: [-1, 0], ArrowRight: [1, 0], ArrowUp: [0, -1], ArrowDown: [0, 1] }[e.key];
    if (!direction) return;
    e.preventDefault();
    const step = e.shiftKey ? 40 : 10;
    move(direction[0] * step, direction[1] * step);
  });
  new ResizeObserver(() => move(0, 0)).observe(bounds);
  new ResizeObserver(() => move(0, 0)).observe(card);
}
