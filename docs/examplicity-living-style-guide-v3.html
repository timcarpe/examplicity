Living lab design language · updated 5 September 2026

Style the real lab, not a diagram of one.

The normative examples in this guide execute current Examplicity lab source. The reviewed pilots retain their authentic models while applying open working layouts, consistent controls and purposeful copy. This living guide incorporates the latest user feedback; older reference wording does not override these rules.

1
Source-fidelity ruleFuture authoring agents should begin from the complete reference implementation or an equivalent authentic model. A simplified mock card, generic network sketch or dashboard abstraction is not a substitute for the actual lab topology. Component plates below document state styling only; they are never lab templates.

Non-negotiable rules

These rules govern the shared language without standardising lab geometry. They apply to current and future labs, including literal reference specimens below.

01No unilateral state rails.

Fields receive complete semantic borders. Other feedback elements receive the full yellow, green or red surface, with a check or x for correct and incorrect states.

02Visual evidence first.

Current costs, distances, memberships, routes, signals and measurements belong on or immediately beside the represented model. Persistent working belongs on the right, then below the model on narrow screens. Keep the same calculation rows when assistance changes.

03Rounded actions, not pills.

Pills are reserved for syllabus chips. Buttons, tabs, mode controls and phase actions use the shared rounded rectangle.

04Reviewed references demonstrate the rules.

The guide shows full current lab code for Binary Number Practice, Coordinate Distance and Graph Search. Do not infer that a stripped-down mock is an acceptable replacement.

05Working stays persistent.

Interaction cues identify a target. Phase cards summarise a reached state or introduce a new decision. Predictions and calculations remain persistent outside them. Stage details may show a read-only working history; they never replace the working column.

06Use space before boxes.

Use padding within one parent surface. Ordinary working uses regular ink-coloured text; reserve borders for fields, feedback and meaningful groups.

07Text must earn its place.

Keep goals, interaction hints, working and non-obvious interpretation. Improve the visual before adding prose that retells it.

08Vertical flow is allowed.

Keep working, evidence and explanation readable. Do not compress a complete lab merely to keep every section inside the first viewport.

Working: None / Some / All

One plain label, no “Working required” heading or helper paragraph. The white selected segment sits inside a light grey group. None reveals the working; operating the model is still required.

Progress without a counter

Place the markers immediately to the right of Working. Use a blue inset dot for current, a green check for complete and empty circles for upcoming. Omit numeric fractions and internal labels such as “calibrate”. Do not invent stages or assistance levels.

Details show actual work

Current evidence follows the model. Completed stages retain their working. Future stages describe the task without exposing answers. Markers report progress and open details; they do not bypass learner action.

Hover, keyboard and touch

Provide the same detail on hover, focus and tap. Keep it open while the pointer enters it; Escape dismisses it and moving focus away closes it. Keep text and controls within the viewport.

Shared values: group #f7f8fa, group border #e7e8eb, selected surface #ffffff, selected border #d2d2d7. Labels are regular 12px; detail copy is 14px. The full Coordinate reference demonstrates all assistance levels and the actual construction sequence.

Let the visual show

Copy review is part of the redesign, including the bottom of each lab. Shortening every old paragraph is not enough: remove repetitions and expose useful evidence directly.

Give each sentence a purpose

Text should establish a goal, enable an interaction, show working, identify a non-obvious state or explain a relationship. If a nearby visual, label or control already communicates it, remove the repetition.

Improve the model first

Label the object, show its changing value, connect the cue to its handle or align comparison values. Do not narrate visible changes underneath the model.

Show results when they exist

Remove empty bottom panels, placeholder working, generic summaries and “results appear here” copy. Compare actual routes, costs and measurements without repeating those metrics in prose.

Keep the reasoning

Retain calculations, the reason a choice is valid, the meaning of a heuristic and qualifications such as legal ties affecting settled counts. Essential screen-reader announcements can repeat a visual change without adding visible prose.

Authoring and review checks
Use the full reference labs to judge the quality of future work. Component plates describe surface grammar; they do not authorise reducing the model to those plates.

  

    
01
Trace every example to a real lab or Lab Kit primitive.
Record the source file and deliberate patch. Do not invent a schematic stand-in when a current lab already demonstrates the topology.

    
02
Keep model evidence on the model.
Graph costs, equal-distance probes and binary place value stay in their visual systems. Working stays in one open column on the right, below the model on narrow screens, with consistent rows across assistance levels.

    
03
Distinguish state from progression.
Yellow, green and red judge current work. Blue cues and upgrade offers introduce an action or a future support decision; they do not mean incorrect.

    
04
Preserve direct manipulation and keyboard parity.
Use the same underlying variable for pointer drag and arrow-key adjustment. Keep the cue attached to the actual rendered target after layout changes.

    
05
Allow the page to extend.
Test at the publication rail and responsive breakpoints, but do not shrink core work or phase copy to satisfy an arbitrary first viewport.
